# PakPerk 项目技术难点与解决情况

以下两点均来自已落地的系统机制，而非功能罗列。文中的“已完成验证”包含项目团队在服务器和移动端的实际测试；代码仓库中的接口契约、数据模型与自动化测试用于复核实现边界。

## 1. 将异构学术论文转化为可阅读、可定位、可追责的结构化内容

**难在哪里。** 学术论文不是规整的网页：同一篇论文中往往同时存在多级章节、双栏文字、跨页表格、图注、公式、引文和不同版本。若只把 PDF 转成纯文本，段落顺序、表格结构和公式极易错位；更严重的是，AI 问答、摘要或批注一旦不能精确回到原论文，用户便无法核验结论，错误内容也没有可追溯的纠正路径。论文版本更新后，旧批注还可能被悄然锚定到错误位置。

**我们解决了什么。** 后端以 GROBID 为基线解析器，将解析结果归一化为“文档代际—章节树—内容块—行内跨度”的模型。每个文本块、图表、公式和引用均保存稳定键、页码/源定位器、内容哈希和解析器版本；AI 的每条结论只允许引用当前论文代际中已检索到的证据块，找不到证据即拒答。对于表格、图像和公式，不做看似自然但不可验证的补全：表格保留网格或纯文本降级结果，公式渲染失败时展示可选中的原始公式，图像定位不可信时直接回退至对应 PDF 页。新版本论文发布后，系统再以稳定键、精确引文和受限相似度进行批注重锚定，并将“自动确认、待确认、孤立”分别记录，避免静默错配。

**可佐证结果。**

- 已在服务器上对**数百篇**论文进行批量处理尝试，覆盖常规正文以及含图、表、公式和引用的复杂论文；处理链路可异步重试，阅读端不会因单篇论文解析失败而被阻塞。
- 单篇文档在移动端采用按需分页和取消旧请求的策略，并设定**最多 2,000 个内容块**的设备侧预算，避免超长论文一次性加载导致内存和交互失控。
- 解析、生成和版本差异均保留论文代际、来源块/对象、模式或提示词版本等证据字段；原始论文始终可一键打开复核。这使“能生成内容”升级为“每项内容都能回到原文核验”。

## 2. 在弱网、多设备和账号切换下实现待读库的可靠同步，而不触发论文处理

**难在哪里。** “收藏/待读”表面只是一个按钮，实际会同时遇到离线点击、重复请求、应用被杀后重启、两台设备相反操作、令牌失效以及账号 A 切换到账号 B 等情况。若只依赖客户端本地状态，容易出现重复保存、已删除条目复活，甚至把 A 的操作发送到 B 的账号。与此同时，保存一本论文不应触发 PDF 下载、解析或模型任务，否则用户的高频轻操作会挤占服务器的重计算资源。

**我们解决了什么。** 服务器以“每账号递增版本号 + 操作 UUID + 删除墓碑”作为唯一事实源：保存和删除操作可幂等重放，复用同一 UUID 却改变论文或意图会被拒绝；客户端将本地状态与操作记录在同一事务中，并用持久化 outbox 在断网恢复后重试。同步引擎按论文串行处理、保留原操作 ID、使用指数退避和 `Retry-After`，并通过版本围栏合并跨设备变更。账号切换时，旧账号的缓存和待发送操作会先撤销和清理，只有令牌、账号 ID 与认证 epoch 三者同时匹配才能发送或写回结果。保存/删除路径在接口和服务层明确禁止触发 arXiv、PDF、GROBID、模型或准备队列任务。

**可佐证结果。**

- 移动端确定性验证覆盖**500 篇缓存论文、100 条已保存记录、200 篇连续分页**以及相同 UUID 的 outbox 恢复、丢包、延迟返回、离线重试和双端同步等场景；服务端还完成过真实 OIDC 与两客户端的保存—重放—删除—墓碑同步闭环，双方最终收敛到同一修订版本。
- 已在 **Android 与 iOS** 系统完成测试；客户端同时具备原生 Android/iOS 工程和 Flutter 统一业务层，减少了两端对同步语义的实现偏差。移动验收方案进一步将四类物理使用形态（Android 手势、Android 三键、iPhone、iPad/第二同步端）拆为 **42 个有序场景、317 条断言、254 个量化指标**，用于持续复核跨端一致性与阅读体验。
- 启动和打开性能设有明确阈值：缓存首个可读帧 **p95 不高于 1,500 ms**，页面打开过渡 **不高于 700 ms**。这些指标使离线优先不只是“有缓存”，而是可度量的可用性目标。

> 说明：数百篇服务器批处理及 Android/iOS 实测为项目已完成的部署验证；仓库保留的是实现、契约和可重复执行的测试代码。涉及正式商店签名、生产发布或大规模线上运行的数据，不以本文件替代其独立验收证据。
