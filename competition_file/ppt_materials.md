# Pakperk 15 页答辩 PPT 素材

> 用途：供答辩 PPT 制作与现场讲述使用，不是项目实现方案正文。  
> 叙事目标：让评委相信 Pakperk 不是“套壳论文聊天”，而是一套尊重研究者注意力、以证据为硬约束、能够沉淀长期研究资产，并具备真实产品化边界的移动科研基础设施。  
> 事实口径：页面中的“已实现”“固定语料验证”“待生产验收”必须严格区分；完整技术与合规依据见 [draft.md](./draft.md)。

## 总体叙事

汇报的沟通目标是：**让评委相信 Pakperk 不是又一个“套壳论文聊天”，而是一套尊重研究者注意力、以证据为硬约束、能够沉淀长期研究资产，并具备真实产品化边界的移动科研基础设施。**

建议采用“背景与矛盾 → 现有方案的断点 → 产品原则 → 用户体验 → 技术可信性 → 实现证据 → 长期价值”的累进结构。页面只保留结论、数字和关键路径，详细边界放在讲述中。优先使用真实 App 截图、真实处理状态和真实证据跳转；不要用大段代码、密集架构框或未经证实的市场规模。

建议视觉系统：16:9；深海蓝/墨黑作为主色，米白作为阅读底色，珊瑚橙只用于“用户意图/关键动作”，青绿色用于“可信证据/已验证”。封面标题不小于 50 pt，页标题不小于 35 pt，正文尽量保持 18–24 pt；每页只讲一个主要结论。

## 第 1 页｜封面：Pakperk 让论文阅读可验证、可积累

页面正文：

> **Pakperk**  
> 把刷论文，变成可验证、可积累的移动研究  
> Queue First · Evidence First · Memory by Choice

页脚只放“AI + 科研阅读与知识管理”，不要放团队成员或指导教师姓名。

画面建议：一部手机从 Abstract 滑向 Introduction，再滑向 Connections；背景只保留淡化的论文段落和一条发光证据线。

讲述重点：开场不先报技术栈，先给判断——“我们不是替用户读论文，而是让用户决定读什么，并能核验 AI 帮他理解了什么。”

## 第 2 页｜论文增长速度，已经超过个人注意力带宽

页面标题：**2025 年 arXiv 新增 284,486 篇论文，稀缺的不是内容，而是研究者的注意力**

页面正文只保留三个信息：

- **284,486 篇/年**
- **约 780 篇/自然日**
- 研究者真正缺少的是：选择、理解、核验、复用

画面建议：以“284,486”为全页主数字，右侧是一条越来越拥挤的论文流，最后收束到一部手机和一个人。

讲述重点：不要把问题说成“论文太长”。真正的系统性矛盾是论文供给持续增加，而人的时间、注意力和核验能力没有增加。[1]

## 第 3 页｜科研阅读被割裂成五个工具，价值在切换中流失

页面标题：**找到论文只是开始，真正的成本发生在工具之间**

页面正文：

```text
搜索/推荐 → PDF 阅读 → AI 问答 → 引用追踪 → 笔记复习
```

在流程下方放四个断点：

- 推荐越用越多，To Read 越积越长
- 小屏 PDF 阻碍连续理解
- “有引用”不代表引用支持结论
- 笔记与论文版本脱节，读后难复用

画面建议：五个工具窗口之间用断裂的箭头连接，中间标出“上下文丢失、重复检索、无法核验”。

讲述重点：把评委从“做一个 PDF Chat 就够了”的直觉，引到“需要重构完整阅读工作流”。

## 第 4 页｜相关工作证明了需求，但仍以单点能力为中心

页面标题：**行业已经解决局部问题，Pakperk 选择连接完整阅读闭环**

页面正文建议做四行对照：

| 代表产品 | 公开主打 | Pakperk 的连接点 |
| --- | --- | --- |
| Semantic Scholar / Reader | 快速筛选、增强阅读 | 加入 Queue-first 与长期研究记忆 |
| SciSpace | PDF 问答与引用 | 加入服务端证据校验和按需处理 |
| Connected Papers | 相似论文关系图 | 用真实引用上下文解释“为何引用” |
| Elicit | 多论文检索与证据综合 | 从可信单篇阅读对象走向未来 Project |

画面建议：不要画“我们全优”的雷达图。以一条研究流程展示每个产品重点覆盖的区段，Pakperk 用一条连续线贯穿“选择—阅读—核验—记忆”。

讲述重点：承认竞品的成熟价值，强调产品中心不同，避免经不起追问的绝对化比较。[2][3][4][5][6]

## 第 5 页｜核心产品原则：先完成已选论文，再推荐下一篇

页面标题：**推荐不应制造更多负债，而应先尊重用户的阅读承诺**

页面正文：

```text
活动 To Read > 0 / 状态未知 / 有待同步保存
                ↓
          只允许队列论文

服务器证明活动 To Read = 0
                ↓
   Recent / Following / For You / Explore
```

旁边放一句大字：**Queue First = Attention by Design**

画面建议：左侧是装满的阅读队列，右侧推荐入口处于关闭；最后一篇被用户显式完成并经服务器确认后，推荐入口才打开。

讲述重点：这是 Pakperk 最容易被记住的创新。它不是 UI 排序，而是贯穿数据库 revision、服务端快照、离线状态机、游标和跨设备同步的系统不变量。

## 第 6 页｜一条连续路径完成“发现—理解—核验—沉淀”

页面标题：**一次阅读，不再跨越五个互不相干的工具**

页面正文用 6 个动词：

> **Add → Queue → Read → Verify → Connect → Remember**

每个动词下只写一行：

- Add：URL / arXiv ID / 标题 / Search / Connections
- Queue：Inbox / Read next / Reading
- Read：Abstract / Introduction / Connections
- Verify：claim 级证据与原文跳转
- Connect：引用理由而非相似度幻觉
- Remember：批注、证据卡、Checkpoint、Memory

画面建议：用一条向前的连续轨道保留 6 个动词，但只配“加入队列—证据核验—保存记忆”3 张真实界面关键帧；不要做六个独立卡片墙。

讲述重点：说明所有动作共享同一论文身份、版本 generation 和来源对象，因此阅读成果不会在工具切换中丢失。

## 第 7 页｜二维手势把小屏限制变成稳定的阅读心智模型

页面标题：**纵向换论文，横向加深理解；三种深度读同一份来源**

页面正文：

```text
纵向：上一篇 ↕ 下一篇

横向：Abstract ↔ Introduction + Assistant ↔ Connections

深度：Skim / Read / Inspect
```

再放一句：**第一次提交到 Introduction，才触发全文准备。**

画面建议：用真实手机录屏的 3 个关键帧。把第一次进入 Introduction 后出现的 `queued → parsing → ready` 作为现场 Demo 起点。

讲述重点：按钮和阶段标签与手势等价，兼顾可发现性和无障碍；Assistant 是 Introduction 上的独立面板，不是第四个横向页面。

## 第 8 页｜可信问答的关键不是“显示引用”，而是“验证引用”

页面标题：**模型只能引用系统给过的证据，证据不足就必须拒答**

页面正文用一条信任链：

```text
当前论文 + 当前 generation
→ 关键词/向量混合检索
→ 结构化 claim + evidence
→ 校验 block、页码、章节、字符范围
→ 回答或明确拒答
→ 一键回到原始来源
```

页面角落写三条硬约束：

- 论文正文是“不可信数据”，不是指令
- 虚构 evidence ID 直接丢弃
- 来源徽章由数据库重建

画面建议：一条回答中的某个 claim 高亮，箭头直达论文原段落；旁边放一个错误证据 ID 被红色拦截的示意。

讲述重点：Pakperk 把 RAG 的来源问题进一步落成可测试的程序约束，而不是依靠提示词“请不要幻觉”。[7][8]

## 第 9 页｜系统架构围绕“可渐进、可失败、可回滚”设计

页面标题：**移动端先可读，后台按能力逐步就绪，单点失败不抹掉已有价值**

页面正文只画五个主体：

```text
Flutter App
    ↓
Axum API ↔ PostgreSQL + pgvector
    ↓                 ↑
Tokio Worker → arXiv / GROBID / Model
```

在流程下方写：

> metadata → Introduction → Assistant → Connections → Deep Reader objects

右下角放三个标签：**幂等任务 / generation 隔离 / feature-gated rollout**

画面建议：用扁平流程，不要塞入全部微模块。把能力逐步点亮作为主要视觉。

讲述重点：模块化单体减少初期运维复杂度；PostgreSQL 同时承担事务、向量、revision 和租约队列，未来只有在真实规模证据出现后才拆服务。

## 第 10 页｜难点一：把易变 PDF 变成长期可引用的研究对象

页面标题：**解析不是抽取一段文字，而是让所有阅读资产共享稳定来源**

页面正文：

- 章节、段落、引用、图、表、公式、术语 → 统一文档对象
- `paper_id + generation + stable key + source locator`
- 新版本：旧能力失效，差异可见，批注保守重定位
- 不确定匹配进入人工复核，不静默“猜对”

画面建议：左侧杂乱双栏 PDF，右侧展开为文档对象树；一条批注从 v1 指向 v2 的精确匹配，另一条进入“需复核”。

讲述重点：这是 Research Memory 能长期成立的技术基础；如果没有稳定来源，批注、证据卡、版本对比和 Agent 都只是不可审计的文本碎片。

## 第 11 页｜难点二：离线与并发不能破坏用户控制权

页面标题：**本地看起来为空，不等于服务器证明队列为空**

页面正文用 5 个状态：

> unknown · local non-empty · pending save · server-confirmed non-empty · server-confirmed empty

只突出一个规则：

> **除 server-confirmed empty 外，全部禁止推荐。**

页面下方再写：

- per-user revision 防止旧游标和晚到响应
- outbox 支持离线保存与重放
- 保存推荐后立即取消剩余推荐导航

画面建议：两部设备同时操作 Library，中间服务器 revision 前进；一个旧推荐响应到达时被丢弃。

讲述重点：技术难点不在“能同步”，而在离线、跨设备、账号切换和失败恢复时仍不越过用户意图。

## 第 12 页｜创新组合：注意力、证据、成本与记忆同时受控

页面标题：**真正的创新不是功能数量，而是四条原则互相约束**

页面正文建议采用一个四层同心结构：

1. **Queue First**：主动队列拥有自动下一篇的决定权
2. **Intent as Compute Boundary**：明确深读才允许全文计算
3. **Evidence First**：claim、来源、版本和字符范围可验证
4. **Memory by Choice**：用户选择什么值得记住，记忆默认私有

同心结构外圈写：**Progressive Capability + Safe Rollout**

画面建议：四层结构中心是“研究者”，不是 AI 模型。

讲述重点：四个创新分别解决注意力、成本、可信度和长期价值；它们共同把 Pakperk 从“功能集合”变成一套有清晰哲学的产品。

## 第 13 页｜我们用真实管线和固定评测集证明它不是概念稿

页面标题：**真实论文、真实异步处理、可复核结果**

页面正文使用 5 个大数字：

- **6** 篇真实 arXiv 演示论文
- **15/15** 问答案例符合固定人工复核预期：10 支持回答 + 5 正确拒答
- **6/6** 关键连接通过四维人工检查
- **约 30 秒** LoRA 本地按需处理：7 个 Introduction 段落、64 条参考文献、5 个关键连接
- **90 / 115 / 24** OpenAPI 路径 / 操作 / 数据库迁移

页脚必须写小字：**固定语料与指定实现结果，不代表跨学科准确率或线上 SLA。**

画面建议：真实 Demo 论文封面/卡片、评测勾选和处理时间轴，不放泛化的“AI 大脑”图片。

讲述重点：把“效果不错”转化为可重放语料、模型/解析器版本、人工标签和失败边界。评委追问时主动说出适用范围，反而增强可信度。

## 第 14 页｜产品价值来自可持续使用，而不是一次惊艳回答

页面标题：**Pakperk 的长期价值，是把每次阅读变成可复用研究资产**

页面正文分三层：

- **个人：** 少切换、少重复检索、答案可核验、阅读可继续
- **高校/实验室：** 可替换模型、可导出证据、可审计版本、可控部署成本
- **生态：** 按需计算减少浪费，原始来源始终可达，高风险功能按证据开放

页面底部写：

> 模型会升级，但 Queue authority、Provenance、Version graph 与 Private memory 会持续积累。

画面建议：由一次阅读产生批注、证据卡、版本记录、Memory，逐渐形成个人研究网络。

讲述重点：这页回答“为什么有前瞻性、为什么不会被下一个大模型替代”。护城河不是某个模型，而是长期可信状态、用户资产和产品治理。

## 第 15 页｜未来：从读懂一篇论文，到运行可审计的研究项目

页面标题：**下一站不是自动替人研究，而是可审计的人机协作**

页面正文用三段路线：

```text
现在
完成代表性评测、签名设备、真实 staging、版权/隐私/AI 标识与公开发布门槛

下一步
多论文 Projects、证据矩阵、方法/结果/限制比较、复现实验清单

长期
Auditable Agent：每一步检索、抽取、比较和写作都有来源、版本与人工确认
```

收束句放在页面中央或底部：

> **Pakperk 想成为的，不是会替你读论文的聊天机器人，而是尊重注意力、证据与记忆的移动研究基础设施。**

画面建议：从一篇论文的证据线，扩展为多篇论文的可追溯研究网络；最终仍由“研究者确认”节点收束，不要以“全自动 Agent”作为终点。

讲述重点：用这句话结束，不需要单独的“Thank You”页。答辩提问自然进入产品边界、评测和路线图。

## PPT 制作与现场演示注意事项

1. **真实界面优先。** 第 6、7、8、13 页尽量使用当前 App 截图或短录屏关键帧；没有实现或尚未启用的界面必须标注“默认关闭/未来路线”，不能用高保真概念图冒充现状。
2. **演示只走一条主链。** 建议选择 LoRA 论文：从 Abstract 第一次进入 Introduction，展示真实 `queued → parsing → ready`；随后问一个可回答问题和一个错误前提问题，再打开一条 Connections 证据。不要在现场遍历所有设置页。
3. **准备离线兜底。** 保留同一版本的录屏、固定语料和评测截图。现场网络失败时明确说明“当前展示的是同一普通管线的已保存证据”，不要假装实时。
4. **主动说清边界。** 固定语料不是通用准确率；约 30 秒是本地一次记录；Deep Reader/评论等高风险能力默认关闭；公开生产发布仍需外部证据。这些不是削弱，而是项目对科学性和产品责任的坚持。
5. **避免三类低价值页面。** 不做大段目录、不贴整屏代码、不用没有来源的市场规模和节省百分比。每页标题直接给出评委应记住的结论。
