# 生产事件响应运行手册

**主要负责人：** 值班事件指挥官。**必需的专业负责人：** 根据受影响边界，由服务、数据库/恢复、身份、隐私、安全/内容审核及发布负责人参与。

## 宣布事件并控制影响

创建一份持久化事件记录，确定严重等级、指挥官和时间线，并使用汇总标识符。绝不要把令牌、秘密值、原始地址、提供商主体标识、电子邮箱、用户名、评论正文或删除账本密文粘贴到聊天或工单中。保留相关的不可变发布证据、审计证据和带校验和的证据，并将访问权限限制在响应人员范围内。

控制较窄范围的写操作时，应保护匿名阅读能力：

- 对于 Plan 03 事件，应先关闭 `DOCLING_EXPERIMENT_ENABLED`，再根据受影响的依赖关系依次关闭 `VERSION_DIFF_ENABLED`、`RESEARCH_MEMORY_ENABLED`、`ANNOTATIONS_ENABLED`、`ASSISTANT_V2_ENABLED`、`VISUAL_OBJECTS_ENABLED`、`SEMANTIC_FACETS_ENABLED`、`PAPER_PASSPORT_ENABLED`，最后关闭 `DEEP_READER_ENABLED`。保留私密产物、旧版 Introduction/来源访问能力和 schema 24。解析器回滚必须恢复到最后一个已验证的 GROBID 配置，且不得合并适配器；
- 如果发生私密研究数据泄露，应停止受影响的路由和遥测导出，保留仅限授权访问的证据，在安全的情况下保持账户删除可用，并验证移动端普通 SQLite 数据的清理边界。不得声称 Drift 数据库提供应用层加密，也不得在控制事件期间部署未经审核的 SQLCipher/密钥迁移；
- 如果阅读 Feed 不变量或队列权威性触发告警，应先关闭 `TO_READ_FIRST_ENFORCEMENT_ENABLED`。关闭 `NOTIFICATIONS_ENABLED` 后再关闭 `SUBSCRIPTIONS_ENABLED`，随后关闭 `READING_BRIEFS_ENABLED` 和 `RECOMMENDATIONS_ENABLED`，最后才关闭 `READING_FEED_ENABLED`；可选事件流可以单独关闭。队列权威状态未知时，绝不能回退到推荐内容；
- 发生搜索/导入事件时，应分别关闭 `PAPER_TITLE_SEARCH_ENABLED` 和 `LIBRARY_IMPORT_WRITES_ENABLED`；只有两个使用方都已关闭后，才能关闭 `PAPER_RESOLUTION_ENABLED`；
- 发生互动功能事件时，应关闭 `NOTIFICATIONS_ENABLED`，之后再关闭 `SUBSCRIPTIONS_ENABLED`；同时应先于阅读 Feed 关闭 `READING_BRIEFS_ENABLED`；
- 发生排序、反馈、说明或事件流问题时，应关闭 `RECOMMENDATIONS_ENABLED` 以及独立的 `RECOMMENDATION_EVENTS_ENABLED`。如果阅读 Feed 仍保持启用，只能继续提供受权威状态约束的最小 Recent 回退内容，而且仍须先证明队列为空并执行最终修订号复核；不得在队列未经验证时因此暴露推荐内容；
- 关闭 `SAVED_QUERIES_ENABLED` 后再关闭 `SEARCH_EXPLORE_ENABLED`，并且只有 Explore 关闭后才能关闭 `SEARCH_LOOKUP_ENABLED`。这些显式搜索开关绝不授权系统自动向 Feed 插入内容；
- 对于用户资料/隐私事件，关闭 `RESEARCH_PROFILES_ENABLED`；对于扩展 Library 事件，关闭 `LIBRARY_V2_ENABLED`；在安全的情况下保留它们所依赖的账户/Library 读取能力；
- 使用 `LIBRARY_WRITES_ENABLED=false` 冻结 Library 写操作；
- 使用 `COMMENT_CREATION_ENABLED=false` 停止发布新内容，同时保留读取、举报/屏蔽、作者删除和内容审核能力；
- 只有完整依赖链不安全时，才停用账户/删除开关；删除 worker 和账本必须继续由隐私负责人控制；
- 扩缩容或隔离发生故障的论文/提供商路径时，不得移除缓存论文的读取能力；以及
- 如果验证或脱敏失败，应停止遥测入口/导出。移动遥测采用尽力而为方式，产品行为不得依赖它。

在控制事件期间，不得销毁证据、清除删除记录、编辑已签名账本文件、执行临时编写的破坏性 SQL、扩大网络 CIDR、信任任意转发请求头，或降低 TLS/认证验证要求。

## 按边界分诊

- **凭据/签名泄露：** 在提供商处撤销或轮换相关材料，更新外部 Secret，递增 `secret.rotationVersion`，滚动更新所有使用方；只有有界的历史数据仍需要时，才保留旧验证/解密密钥。如果移动端签名密钥受影响，请遵循 Apple/Play 的泄露处置流程，并使用权威的已安装应用身份以原子方式更新关联文件。
- **OIDC 中断/泄露：** 必须认证的路由应在失败时默认拒绝；确认访客阅读仍然健康。撤销受影响的客户端/会话，保留完全一致的签发方/受众配置，不得改用外观相似的签发方主机名。
- **删除积压/恢复风险：** 如果外部账本、密钥、worker 权限探针或队列安全性存在不确定性，应停止账户预配/写入。运行 `verify-ledger`；按照 [account-deletion.md](account-deletion.md) 操作，绝不能跳过任何记录。
- **数据库损坏/数据丢失：** 隔离写操作，选择经过验证的恢复点，并按照 [备份恢复运行手册](backup-restore.md) 操作。流量恢复前，当前独立删除账本是必需条件。
- **UGC 违规/内容审核：** 保留举报/屏蔽/管理安全控制；如果责任归属或 SLA 已经不堪重负，应冻结内容创建，并按照 [moderation.md](moderation.md) 操作。不得泄露私密内容审核理由。
- **隐私/日志/遥测：** 停止受影响的流水线，收紧对所保留证据的访问权限，验证采集器处理器和接收端，确定实际字段/保留期限，并通知隐私/安全负责人。
- **Deep Reader 溯源信息/解析器：** 关闭范围最窄的 Plan 03 开关，拒绝过期代次和虚构的证据 ID，保留原始来源访问能力，并停止受影响的新任务。将论文文本视为不可信数据。如果没有经过审核的触发条件和回滚计划，不得重新处理、重新锚定不确定的批注、更改默认解析器或发布版本差异。
- **供应链/镜像：** 停止提升，查明确切的摘要/SBOM/action 提交；如果溯源信息或签名材料受到牵连，应将其撤销；从干净且经过审核的修订重新构建，并在回滚或分阶段发布前重新扫描。

## 恢复与结束事件

恢复需要通过针对具体原因的测试，还要检查访客阅读、健康/就绪状态、错误/延迟、数据库、队列、删除、内容审核和遥测。当前候选版本应保留 schema 24。按照依赖顺序重新启用 Plan 02：账户/Library；解析，随后分别启用标题搜索和导入；先在关闭强制执行的情况下启用阅读 Feed；Library v2 和研究资料；Lookup、Explore、已保存查询；推荐和可选事件；阅读简报；订阅；通知；最后，只有兼容客户端、SLO/不变量告警、隐私、保留策略和审批门禁都通过后，才启用强制执行。此后，只有重新执行完全一致的受保护门禁，才能按 Plan 03 的分阶段依赖顺序重新启用它。历史 Plan 02 规则是：保留 schema 18，绝不降级到 schema 11。当前对应规则是：不能仅为关闭 Deep Reader 而恢复 schema 18。每次更改开关后，都要观察并保留经过脱敏的证据。不得把执行向下迁移作为功能控制手段。恢复数据库还必须先成功验证并重新应用删除记录，并获得隐私审批。轮换凭据还必须证明旧副本和缓存凭据已经消失。

记录影响范围、发现/控制/恢复时间、受影响版本/数据类别、决策、通知、证据位置、剩余风险，以及修复工作的负责人/日期。至少应在非生产环境中演练凭据泄露、提供商中断、数据库恢复/删除重放和冻结评论创建。仓库测试不能算作一次完整的组织事件演练。
