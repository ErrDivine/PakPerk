# 助手工具：最小改动实施计划

状态：仅为提案；尚未变更任何实现。检查日期为 2026-09-06。

## 1. 建议

以一个有界的、由服务端执行的工具循环，扩展现有的 **Assistant v2**。先从三个可供 LLM 调用的只读工具开始：`search_paper_evidence`、`get_paper_outline` 与 `read_paper_blocks`。在核心循环通过验证之后，再将对象与引用上下文相关工具作为单独的后续工作加入。

保持 Rust 模块化单体、PostgreSQL、当前的文档模型、最终答案 schema、引用验证、历史/溯源信息持久化，以及 Flutter 助手呈现方式不变。使用现有的 `/v1/papers/{paper_id}/assistant` 端点。第一次增量开发不需要任何新的 Agent 框架、MCP 服务器、公共工具 API、数据库、向量存储或后台队列。

本计划将“获取更多信息”解读为：从当前已准备好的论文与声明范围中检索额外证据。这遵循了竞赛提案中明确的当前论文边界。网页浏览、其他论文的全文、个人记忆检索以及写入类工具，将需要单独的范围与证据技术契约。

### 当前的执行路径

```text
Legacy /chat
  validate session/policy/readiness -> embed question
  -> vector + keyword candidates -> RRF -> select up to 6 chunks
  -> ChatProvider.answer -> persist chat exchange

Assistant v2 /assistant
  authorize principal/policy/rate limit -> validate request
  -> AssistantContextRepository.retrieve -> open owned thread
  -> AssistantProvider.answer_with_evidence
  -> provider validation + validate_answer_boundary
  -> persist answer, claims, and provenance atomically -> existing UI
```

v2 的 `paper_blocks` 与 `section_blocks` 查询会对 `document_blocks` 进行排序，排序依据是 PostgreSQL 的 `plainto_tsquery` 与 `ts_rank_cd`，随后再按文档序号排序。它们不会调用嵌入提供方或 RRF。由于它们按排名排序而不要求正匹配，因此可能返回零分区块。其他 v2 范围会检索选择内容、关联对象或 Passport 来源区块。当前上限为十个区块，提供方限制为每个区块 20,000 个 Unicode 标量，总计 100,000 个。

该助手路径中不存在任何工具定义、工具调用分发或迭代式工具结果交换。仅有一个结构化的最终答案 schema，并不等同于工具调用。

## 4. 最小可用工具集

以下工具名称与签名是拟议的内部技术契约。它们并不是新的 HTTP 端点。LLM 只提供任务参数；主体、论文 ID、生成代次、原始范围、截止时间与预算，均来自服务端创建的不可变 `AssistantToolContext`。

### 4.1 `search_paper_evidence`

参数：`{ query: string, section_kinds?: SectionKind[], limit?: integer }`。

- `query`：1–500 个 Unicode 标量；不含 NUL。`limit`：1–6，默认为 4。章节过滤器使用现有枚举，且只能收窄原始范围。
- 在当前论文/生成代次范围内，搜索已准备好的 `document_blocks`。复用 v2 的词法排序，但为这种新的搜索方法新增一个显式的正匹配判定标准，以免不相关的开头段落被报告为搜索命中项。
- 返回来源区块 ID、规范文本、可信的章节/页码元数据，以及一个封闭的结果，例如 `ok` 或 `no_matches`。模型可以在其剩余的调用预算内重新表述查询。
- 保持原始用户问题不变。一次重新表述的搜索查询是一个独立的检索参数，绝不能成为保存到历史记录中的替代性 `AssistantRequest.question`。
- 不得将生成的 Passport 正文、旧的助手响应或关系摘要当作事实证据返回。

对于那些所需证据被最初一次性选择所遗漏的问题，此工具是主要的改进手段。

### 4.2 `get_paper_outline`

参数：`{ limit?: integer }`，1–40，默认为 20。

- 返回有界的标题区块 ID、实际可用时的章节路径/类型，以及已知的页码。响应会明确指出是否发生了截断。
- 复用文档大纲数据模型，但为此工具实现一个有界查询。`DocumentReaderRepository::outline` 目前会获取全部标题；在无界获取之后再截断，并不是一个合适的数据库工作量限制方式。
- 将结果限定在原始范围内。当大纲无法提供有用的、被允许的导航时（例如只选中了单个区块），应禁用此工具。
- 将大纲条目视为导航元数据。最终的实质性论断需要被纳入最终证据集合的来源区块。

这让模型能够在搜索或阅读之前，先识别出相关的 Results 或 Limitations 章节。

### 4.3 `read_paper_blocks`

参数：`{ block_ids: UUID[], neighbors?: integer }`，1–4 个不同的 ID；`neighbors` 为 0 或 1，默认为 0。

- 加载确切的区块，并在被允许时，加载同一允许范围内紧邻的相邻区块。每次调用最多返回六个区块。
- ID 可以来自初始证据或此前的工具结果。每个 ID 都必须针对论文、生成代次与范围在数据库中重新验证；仅仅语法有效或此前出现过，并不构成授权。
- 在现有大小限制内返回完整的规范区块文本。绝不能静默截断文本，然后再针对另一个不同的字符串验证偏移量。超大区块会产生一个有界的 `content_too_large` 结果；引入保留偏移量的文本窗口机制被推迟到以后。
- 相邻区块也必须独立通过范围过滤。针对某一章节的请求，不能仅因为其区块序号相邻，就读取下一章节。

这支持精确的来源定位，并能在不加载整篇论文的情况下，恢复被检索段落周围的邻近上下文。

### 4.4 核心功能被接受之后的后续工具

`get_object_evidence({ object_id, kind })` 可以复用当前的图/表/公式所有权检查以及内联片段/上下文区块查找。只返回现有的、范围内的来源区块，外加有界的对象元数据与提取状态。图表说明文字并不能确立未见过的绘图数值。原始表格或公式对象，需要先具备可追溯的区块表示形式，才能在保持不变的答案 schema 下成为论断。请勿为了迁就它们而捏造区块 ID。

`get_citation_context({ reference_id, limit? })` 可以检索当前论文中、其内联引用片段指向该参考文献的区块。请针对同一篇论文/生成代次验证该参考文献，并与原始范围求交集。现有的 `PaperRepository::citation_contexts(reference_id)` 只接受一个参考文献 ID，并获取其全部上下文；它不得被直接公开为一个限定范围的、有界的工具。请添加必要的受防护查询。如果旧版引用文本无法确切映射到某个规范文档区块，请将其从可引用证据中省略。请勿抓取被引用的论文，也不要仅凭标题/相似度来推断关系。

推迟网页搜索、任意 URL/PDF 抓取、跨论文比较、个人笔记/记忆搜索、计算/代码执行、Library 变更以及自动保存。要实现该提案针对当前论文的检索与定位工具，这些都不是必需的。

## 5. 集成设计

将工具编排保留在 API 应用内，使用一个较小的新模块，例如 `backend/apps/api/src/assistant_tools.rs`。提供方适配器了解模型协议；数据库了解来源记录；两者都不应拥有对方那一层的职责。

```text
Existing authorization, scope validation, initial retrieval, owned thread
  -> tool flag + provider capability check
       disabled/unsupported: existing generate_answer path
       enabled: bounded tool-selection loop
         LLM requests named tools -> server validates/executes
         -> bounded untrusted tool results -> optional second selection round
  -> freeze final evidence set
  -> existing structured answer generation with tools absent
  -> existing provider + API evidence checks against that SAME set
  -> existing atomic history/provenance persistence -> existing response/UI
```

### 提供方接缝

以一个默认返回 false 的能力方法，以及一个默认返回不支持结果的工具选择步骤方法，对 `AssistantProvider` 进行增量式扩展。保持 `answer_with_evidence` 不变。这样可以避免为 `ApiModelProvider` 新增另一个必需的父 trait，从而破坏所有现有的提供方替身实现。

在 `llm_provider` 中新增独立的、带类型的工具定义、参数枚举、工具调用 ID、结果与步骤响应；为工具选择使用一个独立的提供方封装。现有的答案封装期望文本内容，而仅工具调用的响应可能没有内容或内容为空。请勿为了迁就任意工具输出而放松现有的最终答案解析器。

对于已配置的兼容适配器，请使用原生的函数工具声明以及助手工具调用/工具结果消息对来实现工具选择。请使用模拟服务器测试以及实现期间的一次有界实时检查，来验证实际部署端点对该协议的支持情况。仅凭适配器系列名称，并不能证明某个已配置的模型支持工具调用。请使用明确的能力/配置选择，而不是对每一个用户问题都进行探测。

工具选择响应可以请求工具，也可以表示已完成。此阶段产生的自由文本绝不会作为答案展示或持久化。在完成选择之后，请发起一次全新的最终 `answer_with_evidence` 调用，其中包含不变的原始问题、有界的现有历史记录，以及已冻结的证据区块。现有的最终 JSON schema 与验证逻辑仍然是权威的。这有意将新的工具协议，与已经可用的结构化答案协议分离开来。

### 证据积累与最终确定

维护一个以 `(paper_id, generation, block_id)` 为键的内存证据注册表。对结果去重，并要求规范文本/元数据保持一致。累计最多允许十个唯一区块；绝不能无限地淘汰再补充。通过为启用工具的分支预先填充不超过四个初始区块，为新的工具结果预留容量。禁用工具的分支保留今天的限制与行为。

在现有标量限制内，最多冻结六个最终证据区块。优先级依次为：强制性的选择/对象证据，确切的已请求区块读取，然后是按排名排序的搜索结果，并使用确定性的平局判定规则。如果强制性证据无法容纳，请保留边界并拒绝不受支持的部分。只有这个最终集合会被提供给生成阶段、经过验证，并作为 `AssistantRetrievalContext` 传递给 `persist_exchange`；如果在根据新区块生成之后再持久化初始上下文，会破坏溯源信息链。

仅在此前某一轮工具调用中出现过的区块，在最终选择之后并不会自动变为可引用。最终生成阶段不会收到任何已丢弃的工具结果记录。大纲与对象元数据在当前的区块范围 schema 下，并不能独立被引用。

保留所有现有的硬性就绪与授权失败情形。如果初始检索因不存在当前文档/范围证据而失败，请返回现有错误；工具绝不能为了绕过该错误而发起准备流程。

### 范围语义

对于论文范围，工具可以搜索当前论文。对于章节范围，请将每个工具过滤器与所请求的章节类型求交集。对于选择范围，保留当前的行为，即把所选区块用作上下文：现有检索会检查所选范围，但会返回完整的区块。请勿声称现有验证会将每一次引用都限制在所选字符范围内。工具的初始增量绝不能将选择范围扩展到其他区块。

对于图/表/公式以及 Passport 字段范围，只允许其现有的来源区块关系，而不允许任意的同论文区块。请禁用不相关的工具，而不是悄悄扩大范围。更宽泛的问题需要在更宽泛的范围内提出一个明确的新请求。

## 6. 可靠性限制与失败行为

使用一个小型静态允许列表，以及会拒绝未知字段的带类型反序列化。不存在动态函数查找、shell 执行、任意 SQL 或由模型提供的端点。即便提供方声称支持严格的 schema，也要在派发时再次验证参数。

拟议的初始预算，有待针对延迟测量结果进行验证：

- 最多两轮工具选择模型调用、四次工具执行总量，以及一次最终答案请求：最多三次逻辑模型请求。
- 单轮最多请求两个工具；初期按顺序执行。在执行之前拒绝超大的批次。每一次尝试执行都会计入次数，包括参数无效与无匹配结果的情况。
- 每次调用最多 8 KiB 的参数 JSON；有界的响应字节数与标量计数；累计序列化后的工具结果最多 256 KiB。所有限制都包含重复出现的结果，而不仅仅是唯一区块。
- 最多十个累计区块与六个最终区块；每个区块最多 20,000 个标量，最终总计最多 100,000 个标量，与现有验证保持一致或更严格。请尽可能在具体化或序列化大型结果之前就强制执行这些边界。
- 一个绝对的端到端截止时间，涵盖数据库工作、适配器重试/退避、工具轮次、最终生成、验证与持久化。请限定 SQL 执行时间，并且不要在等待模型时持有一个打开的事务。

`no_matches` 不同于 `not_ready`、陈旧生成、策略拒绝、超时或提供方故障。真正的证据不足，可能产生现有的 `not_found`/`partial` 答案技术契约。基础设施错误绝不能变成“在本论文中未找到”。未知名称、格式错误的参数、超大负载、重复的调用 ID 以及无效的消息顺序，都会通过有界的、不含内容的错误处理被拒绝。范围违规绝不会返回外部数据。

对于已配置的不受支持的提供方，请在工具执行之前选择原有的 v2 路径。对于运行时提供方/协议故障，请返回现有的错误映射，而不是自动重放另一整条推理路径。这样可以避免隐藏的重复成本。当计划的轮次/调用预算正常耗尽时，如果仍有剩余时间，则使用已采纳的证据进入最终生成阶段；截止时间耗尽会返回现有的超时失败。

使用请求作用域的 future，不使用脱离请求的工具任务，并通过被等待的操作传播取消信号。API 的截止时间必须阻止进一步的工具派发。请勿承诺当客户端断开连接时，上游提供方能够取消已被接受的推理或计费。

在来源读取时重新检查当前生成代次，并在 `persist_exchange` 中保留事务性的生成代次/会话检查。在启用工具的分支中，请在最终发布之前重新检查适用的内容策略。请在模型工作仍在进行期间测试生成替换与账户删除；在陈旧或无效的权威状态下，任何内容都不应被返回或持久化。

### 移动端超时是一个必要的兼容性细节

`mobile/lib/app/account_providers.dart` 中共享的已认证 Dio 实例，具有一个 20 秒的接收超时。`AssistantV2Api.ask` 目前继承了该设置。后端中间件已经将 `/assistant` 识别为一个长时间运行的聊天请求，并配置了单独的超时时间。

规划一个范围狭窄的 `receiveTimeout` 覆盖值（位于 `AssistantV2Api.ask` 中），保留相同的共享 Dio、认证纪元、取消机制以及不自动重试的策略。一个候选预算是：50 秒的、启用工具的服务端操作截止时间，加上服务端路由/代理在此之上的额外余量，以及 65 秒的移动端接收超时；这些是拟议数值，而非经测量的目标值。在启用该开关之前，请验证实际的部署设置与最终生成的时间预留。请勿更改所有 API 请求超时，也不要简单地将现有提供方超时乘以轮次数量。

## 7. 隐私、溯源信息与可观测性

工具只读取共享的、经策略允许的论文产物。现有的助手问答保留机制保持不变；原始工具对话、思维链、搜索查询以及工具参数/结果正文，都不会被加入持久化历史记录、日志、导出内容或遥测数据。

复用现有的答案溯源信息：确切的最终来源区块 ID、解析器/版本、提供方/模型 ID 以及最终提示词版本。为已启用的路径新增一个明确的工具提示词/版本标识符。如果要在溯源信息中保留 `tool_round_count`、`tool_call_count` 或 `tools_enabled`，请使用现有的有界整数/布尔 `ProvenanceParameters` 技术契约，并验证其 schema 与移动端解析；请勿插入任意的对话记录或字符串值追踪数据。目前不计划新增追踪数据表或保留期迁移。

通过现有的可观测性机制，记录有界的工具名称枚举、封闭结果、延迟以及结果计数。不将区块 ID 或问题用作指标标签。汇总提供方在选择调用与答案调用中报告的用量，包括可获取时的失败情况；绝不能只把最终答案的令牌数记为工具运行的总成本。缺失的用量数据仍明确标记为不可用，而不是零或估计值。请使最终完成身份与聚合成本核算保持相互独立。

现有的所有权、私有/不存储响应、反馈查找、账户导出/删除以及过期清理，会继续在不变的答案表示形式上运作。

## 9. 交付顺序与验收标准

### 增量 A：核心工具循环

1. 为现有提供方新增带类型的原生工具选择支持，默认行为为不支持。使用模拟 HTTP 响应验证封装解析与协议时序。
2. 实现这三个只读工具以及不可变的范围/预算强制执行。针对 PostgreSQL，使用同论文、外部论文与陈旧生成代次的测试夹具进行测试。
3. 接入带开关的 v2 分支与最终上下文持久化。禁用时保留原始路径。新增请求截止时间与有针对性的移动端超时处理。
4. 新增有界的可观测性与部署开关接入。运行有针对性的兼容性与行为检查。默认保持开关关闭。

验收要求：一个脚本化模型选择一个搜索查询，收到真实的仓储结果，请求一个来源区块，然后产出一个已验证的答案，其证据在初始种子数据中并不存在。这证明的是真实的、由 LLM 主导的工具使用，而不是一条改了名字的固定检索流水线。

### 增量 B：结构化对象与引用上下文工具

只有在验证了确切的当前生成代次区块映射之后，才新增这两个后续工具。请针对一个表格/公式上下文以及一个真实的内联引用示例进行测试。缺失的映射或仅有说明文字的提取，必须产生一个明确的、有界的局限性/无证据结果，而不是捏造内容。

### 增量 C：可选的混合检索对齐

请勿将这项更大的检索改进，混入这次最小化的工具循环增量中。旧版已索引的 `paper_chunks` 与 v2 的 `document_blocks` 具有不同的 ID 与边界。将向量候选 ID 复用为区块 ID 将是无效的；仅凭同一章节的从属关系，并不构成一个确切的证据映射。

如果日后确实需要，请先针对同一生成代次，使用规范的来源边界/文本，检查并证明一个确定性的分块到区块映射关系。之后 RRF 便可以对已映射的候选项进行排序，但最终的论断仍须引用实际区块。如果无法建立确切映射，请单独评估一次专门的区块嵌入/索引迁移。当向量准备不可用时，请保持词法工具可正常运作。在这项后续工作被实现并评估之前，请将 v2 工具描述为区块词法检索加结构化来源导航，而不是混合 RAG。
