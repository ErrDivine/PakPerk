# Production v0.0 第 5 阶段报告

**阶段：** 评论与内容审核
**状态：** 已完成 — 已接受；公开启用仍是 Phase 6 门禁
**实施快照：** 2026-07-31
**起始提交：** `fefd18e`

这是已接受的第 5 阶段记录。它实现了负责任的扁平化公开论文讨论及其完整的产品内安全边界。它并不表示该功能已公开启用：Phase 6 仍负责端到端账户删除、托管的法务/支持页面、保留/恢复、遥测和告警、商店审核以及签名的发布候选版本控制，因此评论开关尤其是公开评论创建默认保持关闭。

预期的产品与传输行为记录在[评论与内容审核技术契约](../comments-and-moderation.md)中。

**2026-08-01 补漏附录：**原验收记录中的泛称“举报”仅涵盖评论举报。Production v0.0 现在还拥有独立的用户举报表、可安全重复的 API、合并的积压指标、专用的操作人员 list/inspect/resolve 命令、账户删除和备份覆盖，以及显式的移动端**“举报用户”**操作。举报用户不会创建屏蔽，也不会改变可见性。仓库测试覆盖了这一区分；受保护的真实双用户/商店评审证据必须在公开启用前包含新操作。

同一收口用运行时可选择的 HTTPS 适配器取代了休眠的内容审核接缝。确定性规则始终最先运行；提供商中断、无效的状态/正文/schema、重定向和过大的响应都会将评论保留待审而不是发布。Helm 仅为 HTTP 提供商挂载独立的 Bearer 凭据，并将其 URL、超时、Secret 轮换和经评审的 API 出站流量绑定到分阶段发布契约中。管理 CLI 现在通过带有显式近期 `auth_time` 的 OIDC 令牌认证操作人员，要求解析出的本地用户 UUID 位于有界的部署允许列表中，并将该 UUID 派生为被审计的操作者；调用方无法选择操作者标签，普通活跃账户也没有内容审核权限。

**2026-08-09 当前代码树加固附录：**移动端评论边界现在新增了规范化前 6,000 个 UTF-16 代码单元的资源上限和 64 代码单元/64 标量的扩展字素簇上限，会在持久化/传输前拒绝孤立代理项和不安全控制字符，使用与 Rust 权威实现一致的 Unicode 17 NFKC 一致性向量，并在一个去抖动的后台 isolate 中统计较大的已接受草稿。校验待定或无效时，发送和保存保持禁用；过期的校验和草稿恢复结果无法启用或发送不同的可见正文。显式发送的准备是原子性的，并为规范等价的重试意图保留请求 ID，同时为真正不同的规范正文轮换该 ID。Dart 格式化、完整 Flutter 分析、49 项聚焦的 model/repository/API/DAO/controller/widget 测试、Rust 领域回归以及 Android native-SBOM 契约检查均已在当前代码树通过。本附录不会追溯改变下文中 358 项测试的 2026-07-31 验收快照。

## 后端与运营结果

迁移 `0008_comments_and_moderation.sql` 新增规范化评论、唯一举报、持久屏蔽、社区政策接受、内容审核审计，以及最新优先和操作人员队列所需的索引。与传输无关的评论服务会在扣减限额前解析完全一致的创建/举报重放，在提供商工作前检查资格，然后在最终事务内再次检查。编辑使用乐观版本；私有资源的编辑/删除失败会合并为一个公开的未找到响应。共享 PostgreSQL 桶覆盖账户、直接来源、写操作、举报和按目标的举报压力。API 只接受来自已配置入站代理源范围的转发元数据，从右到左解析链路，并在持久化前使用经过验证的仅限所有者密钥对规范客户端地址进行 HMAC 运算。

`COMMENTS_ENABLED` 注册公开读取和安全路由；`COMMENT_CREATION_ENABLED` 只拒绝新发帖。评论限制会在启动时针对领域常量进行断言，`rules` 和有界的 HTTPS 运行时适配器是仅被接受的内容审核提供商，并且必须配置真实且环境安全的支持 URL。确定性的高风险、提供商不确定和提供商中断都会将内容私有保留。经审计的 `pakperk-admin` 二进制暴露不含内容的队列和指标；只有其显式的 inspect 命令会序列化一条选定的正文/举报。

## 移动端与身份结果

Drift schema 版本 5 为访客和每个查看者分别存储有界的评论页面、带稳定请求 ID 的账户/论文草稿，以及持久化的屏蔽投影。所有归账户所有的写入都会经过与退出登录/切换账户清理共享的串行化账户与认证纪元屏障。来自已释放控制器或旧身份的网络完成无法重新填充下一个会话。草稿绝不会进入论文库待同步队列（outbox），也不会在连接恢复后发送；每次尝试都需要显式的发送操作，禁用创建的响应会保留草稿。

论文控件和深层链接路由会呈现访客阅读、显式的登录理由、用户名/条款/社区引导、创建/编辑/删除、举报/屏蔽、我的评论和已屏蔽用户。待审内容仅对其作者可见。本地屏蔽持久化先于远程请求生效并立即过滤；对账会让服务器状态在各个 API 实例间收敛。评论渲染器是纯可选择文本，没有 HTML/Markdown 执行或不安全的自动链接识别。

在该记录的运行之后，仓库验收边界通过专用的公开 PKCE `pakperk-admin-dev` 客户端/受众以及手动、环境门禁、精确 `main` 的工作流得到加强。更新后的测试工具要求先对有效的移动端/API 受众令牌和有效但不在允许列表中的管理受众身份执行单独的负面检查，然后才使用允许列表中的操作人员。它只输出闭合 schema、脱敏、一次性参考证据，并连同卷一起拆除唯一的 Compose 项目。更新后的工作流和 Docker 流程未在本报告中运行；验证器成功只证明仓库技术契约。其 `manual_ci_disposable_reference` 分类不能证明托管环境保护，其 `reference-sha256:` ID 也无法满足生产 Helm `moderationReadinessId`，后者仍要求受保护的预发布环境证据。

## 剩余的 Phase 6 上线门禁

- 应用内与网页账户删除、提供商身份抹除、近期认证、保留和恢复安全的删除台账不由本阶段声称完成。
- 已检入的法务/支持文本仍需要公开 HTTPS 托管、受监控的操作人员详情、合格评审和商店披露签核。
- 模拟器/调试原生构建不能替代受保护的生产签名、真机安全/无障碍流程、TestFlight/Play 评审或 RC 遥测。
- 因此，在 Phase 6 策略门禁被显式接受之前，公开评论创建保持关闭。规范的 Production v0.0 计划及其跨阶段场景仍然是权威依据。
