# 评论与内容审核技术契约

Pakperk Production v0.0 的评论是针对单个论文节点发布的公开、扁平纯文本内容。评论并非私密笔记、同行评审、私信、回复、表态、投票或行内注释。

## 可用性与权限

`COMMENTS_ENABLED=true` 会启用评论读取及相关的已认证安全路由。`COMMENT_CREATION_ENABLED=false` 是独立的紧急写入开关：它只拒绝创建新评论，并返回 503 `FEATURE_DISABLED`；已有评论仍然可读，作者仍可编辑或删除，用户仍可举报评论或用户、屏蔽用户，审核员也仍可执行操作。
两个开关都不会改变访客阅读论文或准备论文的行为。

访客可以列出已发布评论。状态正常的账户无需完成个人资料引导流程，也可举报评论、举报用户或屏蔽其他作者。举报与屏蔽相互独立：用户举报会创建一条私有内容审核记录，但绝不会隐藏内容或自动创建屏蔽关系。创建评论还要求账户设置公开用户名，并接受当前版本的《条款》和《社区指南》。只有作者本人可以编辑或删除评论。
已暂停或等待删除的账户不能对用户生成内容（UGC）执行变更操作。

公开部署必须先在目标环境中实际演练完整的 UGC 政策门禁及已实现的账户删除路径并取得批准，之后才可启用评论创建。开发环境和预发布环境可以启用创建，以演练同一条生产代码路径。

## HTTP 接口

```text
GET    /v1/papers/{paper_id}/comments?cursor=&limit=
POST   /v1/papers/{paper_id}/comments
PATCH  /v1/comments/{comment_id}
DELETE /v1/comments/{comment_id}
POST   /v1/comments/{comment_id}/reports
POST   /v1/users/{user_id}/reports
PUT    /v1/me/blocked-users/{user_id}
DELETE /v1/me/blocked-users/{user_id}
GET    /v1/me/blocked-users?cursor=&limit=
GET    /v1/me/comments?cursor=&limit=
```

创建评论使用一个规范客户端 UUID：

```json
{
  "client_request_id": "0198f4da-383f-77f0-9404-e6d6614d26e1",
  "body": "The ablation in Section 4 changes how I read the main result."
}
```

精确重放会返回已有的规范评论。同一个请求 ID 用于另一篇论文或不同的规范化正文时，返回 `IDEMPOTENCY_CONFLICT`；该错误代码有意区别于 Library 操作 ID 重用冲突。编辑操作携带完整的替换正文和 `expected_version`；版本已过期时返回 `COMMENT_EDIT_CONFLICT`。删除、评论举报、用户举报、屏蔽和取消屏蔽操作均可安全重复。评论举报按举报人/评论组合保持唯一，用户举报则另行按举报人/被举报用户组合保持唯一。两类举报请求正文都采用封闭结构，必须包含 `reason`，并可包含一个有界的 `detail`。省略 `detail` 和显式发送 JSON `null` 都表示未提供详情；未知属性会导致 `INVALID_REQUEST`，与代码优先的 OpenAPI schema 保持一致。

列表按最新优先排序，并使用不透明的 `(created_at, id)` 游标。游标排序坐标采用 AES-256-GCM 加密和认证，并绑定到指定列表用途以及论文/账户/状态作用域。由于账户的屏蔽列表会改变可见结果集，公开论文评论游标还会把论文与明确的访客或账户查看者身份绑定。客户端必须原样返回令牌；来自其他列表、查看者或过滤条件的令牌会被拒绝。
共享且按轮换顺序排列的 API 密钥环可以让活动副本与管理员 CLI 调用保持互操作，同时不暴露时间戳或标识符。
论文评论列表只包含已发布评论。已认证的 `GET /v1/me/comments` 所有者列表是唯一也会展示该作者私有 `pending_review` 记录的列表接口。已认证论文列表会移除被屏蔽作者。容量有界的作者投影仅包含本地用户 ID、公开用户名、显示名称和一个公开状态标记。举报数量、内容审核原因、提供商结论、OIDC 身份和私有账户数据绝不会返回。

针对账户的评论、评论举报、用户举报、屏蔽和所有者列表响应始终是
`Cache-Control: private, no-store`。评论正文和举报详情绝不会写入追踪字段、分析数据、错误消息或调试输出。

## 文本与内容审核规则

服务端具有最终权威。它对输入执行 NFKC 规范化，统一换行符，去除首尾空白，合并异常连续空行，拒绝不受支持的控制字符，并同时执行 2,000 个 Unicode 标量值上限和严格的 UTF-8 字节上限。存储内容是规范化后的原始文本，绝不是 HTML 或渲染后的 Markdown。不支持附件。URL 数量以及确定性垃圾内容/风险检查均有明确上限。

移动端编辑器在校验或计算文本长度前，使用固定版本、采用 MIT 许可证的 `unorm_dart` NFKC 实现和固定版本的 `characters` 字素分割器，执行与服务端一致的规范化。因此，可见计数器报告规范化后的 Unicode 标量值，而不是 UTF-16 代码单元或规范化前的原始输入。原始输入上限为 6,000 个 UTF-16 代码单元，另对扩展字素簇设置 64 个代码单元和 64 个标量值的上限；系统在规范化或持久化草稿前，以线性时间拒绝异常粘贴，同时仍接受 2,000 个补充平面标量值和 2,000 个分解形式的韩文音节。孤立代理代码单元会在 JSON 传输前导致校验失败。较短文本的计数器直接更新；篇幅较大的有效草稿采用防抖处理，并且同一时间最多由一个后台 isolate 执行规范化，过期结果会被丢弃。校验尚未完成或结果无效时，Send 和 Save 保持禁用；包含无效内容的编辑器仍保持打开并显示明确错误。显式发送前的准备步骤会原子比较规范正文意图和上一次尝试发送的规范正文：NFKC 等价或空白等价的重试会沿用请求 ID，只有规范正文确实不同时才轮换 ID。Rust 或 Dart 回归测试覆盖不安全的双向文本/格式控制字符、Unicode 17 NFKC 健全性向量、展开行为、连续空行、标量值/字节边界、URL 上限、异常字素簇和幂等重试意图。服务端仍具最终权威，在创建和编辑时会再次执行规范化以及语义安全、长度和链接检查。

同步执行流水线如下：

1. 规范化和验证。
2. 应用确定性垃圾、URL 和高风险规则。
3. 执行共享的账户及请求来源限流。
4. 重新检查账户/个人资料/社区资格。
5. 如果存在，询问配置的 `ContentModerator`。
6. 发布、拒绝或存储为 `pending_review`。

确定性校验判定无效的内容会被拒绝。命中确定性高风险规则的内容会进入待审核状态。未配置外部适配器时，通过确定性校验的低风险内容可以发布。已配置的适配器不可用或结论不确定时，评论会保持私有，绝不会在失败时放行。审核员输出和错误详情保持私有，诊断信息也不包含评论内容。

`COMMENT_MODERATION_PROVIDER=rules` 选择仅确定性的基线。
`http` 启用与提供商无关的服务端适配器，并要求配置 `COMMENT_MODERATION_URL`、一份仅限所有者访问的 `COMMENT_MODERATION_TOKEN_FILE`，以及可选但不超过 10 秒的超时。部署 URL 必须使用 HTTPS，禁止重定向，响应上限为 64 KiB；接受的 JSON 结构有意保持封闭：`publish` 不带原因，`pending_review` 和 `reject` 则必须包含有界且稳定的 `reason_code`。配置、凭据、请求/响应内容和提供商错误均会脱敏。Helm 值与该技术契约保持一致，提供商地址必须纳入 API 已审核的 HTTPS 出口范围。

请求来源限流绝不持久化原始网络地址。直接开发连接使用对端地址。部署后的 API 要求配置 `API_TRUSTED_PROXY_CIDRS`；只有对端地址属于已审核 Ingress 范围时，才接受其 `X-Forwarded-For`，并沿受信任代理链从右向左遍历，采用遇到的第一个不受信任地址。元数据缺失、格式错误、过大或不受信任时，系统回退到直接对端地址，使调用方无法自行选择一个全新限流桶。选中的地址会立即规范化，并通过 `API_ORIGIN_HASH_SECRET_FILE` 转换为 HMAC-SHA-256 作用域；该地址不会写入日志或持久化。密钥文件必须是仅限所有者访问、不是符号链接的普通文件，并包含 32–4,096 个非占位字节。轮换密钥会有意启用一组新的来源桶，而账户桶保持不变；因此生产密钥轮换必须在防滥用限流窗口内协调进行，旧部署密钥只保留到旧副本及其桶全部过期。

## 设备行为

Drift 针对每个 `(paper, viewer account/guest)` 组合缓存数量有界的页面，并在刷新前先显示缓存。草稿按账户划分作用域，每篇论文最多一份；它们绝不会进入待同步队列（outbox），恢复联网后也不会自动发送。用户必须明确执行 Send；只有服务端接受规范结果后才会清除草稿。`pending_review` 结果仅对作者显示为“正在审核”。`COMMENT_PENDING_REVIEW` 仍是保留的稳定名称，而不是已发出的错误：当前 v0.0 技术契约会接受写入，并返回状态为 `pending_review` 的私有规范评论。

屏蔽状态按账户划分作用域并持久化。屏蔽操作会立即从当前视图移除该作者的缓存评论，服务端过滤则让该选择跨设备持续生效。登出或切换账户会清除草稿、屏蔽投影、个性化页面和进行中的账户工作，同时保留访客可安全使用的公开论文数据。

`USER_BLOCKED` 同样是保留名称，而不是已发出的错误。屏蔽和取消屏蔽属于幂等关系变更操作；列表过滤会移除被屏蔽作者，而不会把其他原本有效的读取变成错误响应。

评论操作菜单分别使用 **Report comment**、**Report user** 和 **Block user** 标签。成功举报用户后，确认信息会明确说明没有同时添加屏蔽；只有显式执行屏蔽操作才会移除该作者的评论。

代码优先的 [OpenAPI 规范文件](openapi-v1.json)是机器可读的线协议技术契约。[API 错误目录](api-error-catalogue.md)区分已发出的错误代码和保留的稳定名称。[内容审核运行手册](runbooks/moderation.md)规定运营响应流程，[社区指南](legal/community-guidelines.md)则规定面向读者的行为准则。
