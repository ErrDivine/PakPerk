# 评论和管理协议

Pakperk Production v0.0 的评论是扁平的、公开的、纯文本的观察，针对一个论文节点。它们不是私密笔记、同行评审、直接消息、回复、反应、投票或内联注释。

## 可用性与权限

`COMMENTS_ENABLED=true` 会发布评论的读取以及相关的认证安全路由。`COMMENT_CREATION_ENABLED=false` 是一个独立的紧急写入开关：它仅拒绝新评论的创建，返回 503 `FEATURE_DISABLED`；已有的评论仍然可读，作者仍可编辑或删除，用户仍可举报评论或用户、屏蔽用户，管理员仍可采取行动。
两个标志都不会改变访客阅读论文或准备论文的权限。

访客可以列出已发布的评论。一个活跃的账户可以在未完成资料注册的情况下举报评论、举报用户或屏蔽另一位作者。举报和屏蔽是分开的：用户举报会创建一个私有的管理记录，但永远不会隐藏内容或创建屏蔽。创建评论还需要一个 handle、当前的条款版本和当前的社区指南版本。只有作者可以编辑或删除评论。
被暂停或处于删除待处理状态的账户不能修改用户生成内容（UGC）。

公共部署会在完整的 UGC 政策门控和已实现的账户删除路径在该环境中经过测试并获得批准后才开启评论创建。开发和测试环境可以启用创建以测试相同的生产代码路径。

列表按最新顺序排列，使用不透明的 `(created_at, id)` 游标。游标排序坐标使用 AES-256-GCM 加密、认证，并绑定到确切的列表用途加上论文/账户/状态范围。公共论文评论游标还绑定论文到显式的访客或账户查看者身份，因为账户屏蔽列表会改变可见结果集。客户端必须返回令牌不变；来自其他列表、查看者或过滤器的令牌将被拒绝。
共享的旋转顺序 API 密钥环保持活动副本和管理员 CLI 调用的互操作性，而无需暴露时间戳或标识符。
论文评论列表仅包含已发布的评论。经过认证的 `GET /v1/me/comments` 所有者列表是唯一展示该作者私有 `pending_review` 记录的列表表面。经过认证的论文列表会移除被屏蔽的作者。有限的作者投影仅包含本地用户 ID、用户名、显示名称和一个公开状态标记。举报计数、管理原因、提供者决定、OIDC 身份和私有账户数据永远不会返回。

针对账户的评论、评论举报、用户举报、屏蔽和所有者列表响应始终是
`Cache-Control: private, no-store`。评论正文和举报详情永远不会放置在追踪字段、分析、错误信息或调试输出中。

## 文本和管理规则

服务器是权威的。它对输入进行 NFKC 规范化，规范化换行符，修剪外层空白，合并病态空行运行，拒绝不支持的控制字符，并强制 2,000 个 Unicode 标量值加上严格的 UTF-8 字节限制。存储的内容是规范化的原始文本，而不是 HTML 或渲染的 Markdown。不支持附件。URL 数量和确定性垃圾/风险检查是有限的。

移动编辑器通过与固定 MIT 许可的 `unorm_dart` NFKC 实现和固定 `characters` 图形段分割器进行规范化的镜像，在验证或计数文本之前。其可见计数器因此报告规范化的 Unicode 标量值，而不是 UTF-16 代码单元或原始预规范化输入。一个 6,000 UTF-16 代码单元的原始上限加上一个 64 代码单元和 64 标量扩展图形簇上限，在规范化或草稿持久化之前以线性时间拒绝病态粘贴，同时仍然接受 2,000 个补充标量和 2,000 个分解的韩文音节。孤立的代理代码单元在 JSON 传输前失败。小计数器直接更新；较大的接受草稿被延迟并规范化，每次最多由一个后台隔离器处理，过时的结果被丢弃。发送和保存在验证待定或无效时保持禁用，无效编辑保持打开并带有明确错误。显式发送准备原子地比较规范正文意图与规范的最后一次尝试正文，保留请求 ID 用于 NFKC 或空白等效重试，并仅在规范正文真正不同时旋转它。不安全的双向/格式控制、Unicode 17 NFKC 健康向量、扩展、重复空行、标量/字节边界、URL 限制、病态簇和等幂重试意图有 Rust 或 Dart 回归。服务器保持权威，并在创建和编辑时重复规范化以及语义安全、长度和链接检查。

同步管道是：

1. 规范化和验证。
2. 应用确定性垃圾、URL 和高风险规则。
3. 强制共享账户和请求来源速率限制。
4. 重新检查账户/个人资料/社区资格。
5. 如果存在，询问配置的 `ContentModerator`。
6. 发布、拒绝或存储为 `pending_review`。

确定性无效内容被拒绝。确定性高风险匹配被保留以供审查。如果没有配置外部适配器，确定性低风险通过可能发布。当配置的适配器不可用或不确定时，评论将被保留为私有而不是失败开放。审核员输出和错误详细信息在诊断中保持私有且内容无关。

`COMMENT_MODERATION_PROVIDER=rules` 选择仅确定性的基线。
`http` 启用提供者中立的服务器端适配器，并要求 `COMMENT_MODERATION_URL`，一个所有者专用的 `COMMENT_MODERATION_TOKEN_FILE`，以及最多 10 秒的可选超时。部署的 URL 是 HTTPS，重定向被禁用，响应被限制在 64 KiB，且接受的 JSON 形状是故意封闭的：`publish` 没有原因，而 `pending_review` 和 `reject` 需要一个有限的稳定 `reason_code`。配置、凭证、请求/响应内容和提供者错误保持被遮蔽。Helm 值镜像此合同，提供者地址必须包含在 API 的审核 HTTPS 出口范围中。

请求来源速率限制从不持久化原始网络地址。直接开发连接使用其对等地址。部署的 API 需要 `API_TRUSTED_PROXY_CIDRS`；它仅接受来自对等地址的 `X-Forwarded-For`，这些地址在审核的入口范围中，通过信任的代理向右向左遍历链，并使用第一个不信任的地址。缺失、格式错误、过大或不信任的元数据回退到直接对等，因此调用者无法选择一个新鲜的桶。选定的地址被规范化并立即成为 `API_ORIGIN_HASH_SECRET_FILE` 下的 HMAC-SHA-256 范围；它不会被记录或持久化。该文件必须是一个所有者专用的、非符号链接的普通文件，包含 32–4,096 个非占位符字节。旋转它故意开始新的源桶，同时账户桶保持不变，因此生产旋转在滥用速率窗口期间协调，且之前的部署秘密仅保留到旧副本及其桶过期为止。

## 设备行为

漂移缓存每个 `(paper, viewer account/guest)` 的有限页面数，并在刷新前显示它们。草稿是账户范围的，每篇论文一个，且永远不会进入同步出站或在连接恢复后自动发送。必须显式发送；草稿仅在服务器接受规范结果后才会清除。`pending_review` 结果对作者私有可见为“正在审核中。”`COMMENT_PENDING_REVIEW` 保持为保留的稳定名称，而不是发出的错误：当前 v0.0 合约接受写入并返回状态为 `pending_review` 的私有规范评论。

屏蔽状态是账户范围的并持久化。屏蔽会立即从活动视图中移除该作者的缓存评论，而服务器端过滤使该选择在设备间持久化。登出/账户切换会清除草稿、屏蔽投影、个性化页面和进行中的账户工作，同时保留访客安全的公共论文数据。

`USER_BLOCKED` 同样是保留的，而不是作为错误发出。屏蔽和取消屏蔽是等幂关系的变更，被屏蔽的作者通过列表过滤移除，而不是将其他有效的读取转换为错误响应。

评论操作菜单标签 **举报评论**、**举报用户** 和 **屏蔽用户** 分别。成功的用户举报确认没有添加屏蔽；只有显式的屏蔽操作移除作者的评论。

代码优先的 [OpenAPI 艺术品](openapi-v1.json) 是机器可读的线协议。[API 错误目录](api-error-catalogue.md) 区分发出的错误代码和保留的稳定名称。[审核运行手册](runbooks/moderation.md) 拥有操作响应，[社区指南](legal/community-guidelines.md) 拥有面向读者的行为规则。
