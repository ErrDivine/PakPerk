# ADR 0005: 共享 PostgreSQL 限流

**状态:** 已接受 —— 通过 Phase 6 实现  
**日期:** 2026-07-31

## 背景

演示中的进程内限流在 API 副本扩展时不够一致。  
认证、保存、公开评论、报告、资料变更、删除以及昂贵的论文操作需要在所有 API 实例之间共享的限流。为这个里程碑引入 Redis 或其他网络服务将违反模块化单体的运营边界，除非有明确的需求证明。

## 决定

使用 PostgreSQL 支持的共享限流桶，通过原子的 `INSERT ... ON CONFLICT ... DO UPDATE` 操作实现固定窗口或滑动窗口。PostgreSQL 仍然是源真值，与现有的租约任务和同步记录并存。将边缘反向代理限流作为额外的粗粒度滥用控制，而不是唯一的应用限流。返回稳定的 `RATE_LIMITED` 错误和 `Retry-After`。

初始桶覆盖评论创建（用户和键请求源）、评论编辑、报告（用户、目标和键请求源）、资料更新、库变更、账户删除和匿名准备/聊天。公共准备/聊天限流器始终消耗键源桶，也可能消耗匿名会话桶；它从不只依赖客户端提供的会话 ID。

## 实现状态

Phase 3 添加了共享 PostgreSQL 桶表、原子固定窗口存储库、有限的清理操作以及第一个 `profile_update` 每用户桶。被拒绝的资料更新映射到稳定的 `RATE_LIMITED` 错误和一个 delta 秒的 `Retry-After` 值。Phases 4–6 将该基础扩展到库、评论/报告、账户删除和准备/聊天。公共操作和评论源范围使用共享的可信代理边界和一个通用的、仅所有者使用的 HMAC 密钥；数据库故障将关闭这些受保护的操作。

## 后果

- 限流状态在副本之间保持一致，可以与产品数据库一起查看、过期、测试和备份。
- 需要新的表/索引、清理任务、事务集成和指标；流量/负载测试必须验证竞争和故障行为。
- 限流变为配置，具有文档化的默认值和审查的产品政策，而不是隐式的进程内行为。
- Redis、Kafka、NATS 和独立的限流服务不在范围之内，除非未来 ADR 改变此决定。

## 安全和运营影响

- IP/设备范围密钥在保留时使用旋转的服务器密钥进行哈希；原始标识符不会被记录或不必要的持久化。
- 桶必须具有有限的保留期和清理过期，以避免无限制增长。监控清理失败、拒绝操作率、数据库竞争和绕过尝试。
- 数据库故障行为必须对敏感写入安全失败，并在服务健康/运行手册中保持明确；边缘控制只提供补充保护。
- 限流不是授权。每个受保护的操作仍然验证已认证的主体并应用所有权/状态/条款检查。
