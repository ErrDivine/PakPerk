# ADR 0005：由 PostgreSQL 共享的限流

**状态：** 已接受——已实现至 Phase 6
**日期：** 2026-07-31

## 背景

当 API 副本横向扩展时，演示版采用的进程内限流无法保证一致性。认证、保存、
公开评论、举报、个人资料变更操作、删除和高成本论文操作，都需要由每个 API 实例
共同执行同一套限制。在没有明确需求的情况下，为这一里程碑引入 Redis 或其他
网络服务，会违反模块化单体的运营边界。

## 决策

采用由 PostgreSQL 支持的共享限流桶，通过原子的
`INSERT ... ON CONFLICT ... DO UPDATE` 操作实现固定窗口或滑动窗口。
PostgreSQL 与现有的租约作业和同步记录一样，继续作为事实来源。
边缘反向代理的限制只作为额外的粗粒度滥用防护，不能成为唯一的应用级限制。
达到限制时返回稳定错误 `RATE_LIMITED` 和 `Retry-After`。

首批限流桶覆盖评论创建（按用户及带密钥的请求来源）、评论编辑、举报
（按用户、目标及带密钥的请求来源）、个人资料更新、Library 变更操作、账户删除，
以及匿名准备/聊天。公开准备/聊天限流器始终会消耗一个带密钥的来源桶，
并且还可能消耗匿名会话桶；它绝不会只依赖客户端提供的会话 ID。

## 实现状态

Phase 3 增加了共享 PostgreSQL 限流桶表、原子固定窗口存储库、
有界清理操作，以及首个按用户计算的 `profile_update` 限流桶。
被拒绝的个人资料更新映射为稳定错误 `RATE_LIMITED`，并返回以秒为单位的差值作为
`Retry-After`。Phase 4–6 将这一基础能力扩展到 Library、评论/举报、账户删除
以及准备/聊天。公开操作与评论的来源范围共同使用受信任代理边界，以及一把通用、
仅所有者可读的 HMAC 密钥；数据库故障时，默认拒绝这些受保护操作。

## 后果

- 限流状态在所有副本之间保持一致，可随产品数据库一同检查、过期、测试和备份。
- 需要新增数据表及索引、清理作业、事务集成和指标；流量及负载测试必须验证争用和故障行为。
- 限制值成为带有文档化默认值并经产品政策审核的配置，而不再是隐含的单进程行为。
- Redis、Kafka、NATS 和独立限流服务均不在范围内，除非未来的 ADR 修改本决策。

## 安全与运营影响

- 需要保留 IP/设备范围键时，使用可轮换的服务端密钥对其进行哈希；原始标识符不得写入日志，也不得无必要地持久化。
- 限流桶必须具有有界保留期，并清理过期数据，以免无限增长。应监控清理失败、被拒操作比例、数据库争用和绕过尝试。
- 数据库中断时，敏感写入必须安全地默认拒绝；这一行为也必须在服务健康检查和运行手册中明确说明。边缘控制只能提供补充保护。
- 限流不等于授权。每个受保护操作仍须验证已认证主体，并执行所有权、状态和条款检查。
