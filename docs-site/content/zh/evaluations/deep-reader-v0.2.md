# Deep Reader v0.2 评估状态

这是一份需求台账，而不是一份评估通过报告。仓库测试可以验证架构、测试固件、门槛和证据绑定。它们无法将受保护的人工审查、真实模型运行、法律审查、预发布环境、遥测、无障碍审查或签名设备演练标记为已通过。

## 当前仓库证据

- 现有的五篇论文内容评估及其 worker 验证器仍是当前聊天与连接行为的兼容性基线。
- GROBID 镜像已锁定版本，TEI 测试固件覆盖当前解析器路径。
- 队列优先验证器覆盖了对齐后的 Plan 02 权限边界。
- `scripts/deep_reader_evaluation.py` 验证一个有界、带版本且不含内容的语料库/标签/观测契约，并生成通过 SHA-256 与这三项输入全部绑定的确定性报告。
- `evaluation/deep-reader-v1/` 包含 Draft 2020-12 架构和生成的合成测试固件，覆盖解析器结构/来源指标、Passport 证据与弃答、Assistant 证据 ID 与方法基线检查，以及视觉对象精度/来源导航。仓库/API 测试还覆盖闭合的 Assistant 证据纠错词汇表、脱敏、响应/论断/块绑定、主体/当前代际隔离，以及幂等回执。其中的 Docling 记录已明确禁用；这并不表示存在任何实验结果。
- `scripts/deep_reader_release_evidence.py inventory` 会发布确切的 23 个 Plan 03 门禁、所需来源类别和闭合断言，但不会给出通过结果。

合成评估器只报告仓库技术契约结果。它不能替代 Plan 03 所要求的代表性解析器语料库、人工 Passport 字段审查、精确候选版本的真实 Assistant 评估、人工视觉精度审查、标注/设备矩阵、阅读研究、法律批准或无障碍结果。

对已实现的 worker 基线也必须作狭义理解。GROBID 是已配置的解析器；经检查的 Docling 观测处于禁用状态，并非基准测试运行。Passport 生成目前采用确定性的来源线索选择，并不能证明领域正确性。版本差异算法 `stable-key-content-similarity-v2` 结合稳定键、精确哈希和有界的内容相似度信号，但它并不是经过验证的语义文本编辑评分。新处理代次现在会触发有界的后台重新锚定：唯一精确匹配可以提交，达到高门槛的模糊候选仍保持不确定；用户可以明确将标注重新附加到较新处理代次中的精确范围，并在私有历史中保留此次移动。仓库测试固件可以证明这些失败时拒绝的形态，但这并不构成启用功能的许可，也不代表通过了人工质量门槛。

仓库尚未完成通过所有受保护门禁所需的每个界面。现在已有一条有界 worker 流水线，可处理经操作员精确审查且限定代际的 PNG 来源。worker 会预检尺寸，解码并重新编码像素以去除辅助元数据，然后原子发布一组与清单哈希绑定的小/中/大版本。已认证路由会验证该清单，以及所选文件的哈希、尺寸、媒体类型、大小、代际和对象范围。移动端会独立验证和缓存各版本。公式采用忠于确切来源、不会修复内容的受维护渲染方式：SmartMath 的清理/输入修复已禁用，格式错误的 LaTeX 或不受支持的 MathML 会回退为可选择的原始文本。对于缺失、链接、格式错误、过大或其他不可信来源，系统会清除陈旧的资源元数据并保留标题/PDF 回退；绝不会推断解析器坐标裁剪，生成无障碍说明的能力仍标记为不可用。仓库测试中的研究 JSON/Markdown/清单导出与原子标注导入，可以往返还原标注、选择器、冲突、合并后的正文，以及完整保留的重新锚定历史。有界研究导出还包括绑定所有者的 Assistant 证据反馈和可选的私有纠错详情；删除级联覆盖则将这些行绑定到同一账户/线程所有权根。差异项目会在来源可信时暴露经过代际检查的对象目标和准确的 PDF 页 URL。大文档架构现在包含闭合的持续窗口、采样、延迟、帧、RSS、widget 和保留预算，但尚无任何已签名实体设备运行通过这些预算。精确候选版本的视觉版权、质量、真实流水线、标注、差异、性能和无障碍结果仍是外部证据缺口。

## 发布结果

`not_ready`：任何已纳入版本控制的产物都不得改变此状态。只有当受保护的发布包中全部 23 个门禁清单都使用同一个精确候选绑定，并包含每一种所需证据类别的通过结果，随后再取得有界的发布负责人批准时，验证才会通过。缺失证据、`pending`、占位符，或以仓库结果替代外部结果，都会导致验证失败。

架构 18 到 24 的迁移/恢复演练同样属于受保护的预发布环境证据。单元测试成功、在未配置数据库时完成真实 PostgreSQL 测试编译、生成 OpenAPI/文档输出，或 Helm 二进制不存在，都不能满足该门禁。

合成仓库报告本身始终包含 `release_status: not_ready`，并将所有 `human_domain`、`legal_review`、`live_model` 和 `signed_device` 来源标记为 `not_ready`。`report-content-id` 只能将该报告绑定到某个门禁的 `repository` 来源；它绝不能满足受保护的来源类别。

有关分阶段发布顺序和回滚流程，请参阅[发布运行手册](../runbooks/deep-reader-rollout.md)。
